# macOS 权限与安全检查

简体中文 · [English](PERMISSIONS.en.md)

MyTerm 没有“一键授予全部权限”的要求。系统弹窗、MyTerm 的 SSH 命令审批和 Codex 的工具审批是三套不同机制。

| 项目 | 何时需要／在哪里查看 |
| --- | --- |
| 允许运行应用（Gatekeeper） | 当前发布包采用 ad-hoc 临时签名、未公证。首次下载后可能需要在“系统设置 → 隐私与安全性 → 安全性”选择“仍要打开”。这是运行许可，不是 SSH 执行授权。请安装到“应用程序”后运行。 |
| 文件与文件夹 | 上传、下载、导出、导入或在本地终端/Codex 中访问桌面、文稿、下载、可移动磁盘或网络卷等受保护位置时，系统可能请求对应访问。只允许任务实际需要的位置；查看“隐私与安全性 → 文件与文件夹”。 |
| 本地网络 | 连接局域网 SSH/SFTP、局域网代理等时，macOS 可能要求本地网络访问。根据系统提示在“隐私与安全性 → 本地网络”查看相关应用。互联网代理或 Codex 登录成功不证明局域网访问正常。 |
| 自动化 | MyTerm 正常终端与 SSH MCP 握手不依赖控制其他应用。终端中运行的 AppleScript、外部工具或开发安装脚本可能要求控制目标应用；按弹窗中实际程序与目标判断。`scripts/install-release.sh` 使用 AppleScript 退出旧 MyTerm，可能向运行该脚本的宿主请求自动化权限。 |
| 辅助功能、输入监控 | 正常键盘输入、应用内快捷键、选择复制和 SSH MCP 不要求开启这两项。代码中的输入监听仅限本应用；不要为修复 MCP 握手而盲目授予。外部自动化工具或用户执行的命令可能有自己的要求。 |
| 屏幕录制、麦克风、摄像头 | MyTerm 的终端与 SSH MCP 功能不要求。Teams 分享屏幕或其他工具所需权限属于对应工具。 |
| 完全磁盘访问 | 不是 MyTerm 或 MCP 的常规前提。只有用户主动执行的本地任务确实需要访问额外受保护数据时，才单独评估；不会自动申请或建议作为通用修复。 |
| 管理员／远端权限 | 替换 `/Applications` 中应用的写权限、本地 `sudo` 和 SSH 远端账号权限，与上述隐私授权分别处理。MyTerm 的“允许执行 SSH 命令”不会授予 macOS 管理员权限。 |

SSH MCP 使用标准输入输出与本机 Unix socket，不使用屏幕截图或辅助功能读取终端。不要通过开启屏幕录制、完全磁盘访问或重置全部隐私权限来尝试修复握手。

## Codex 安装或升级后的首次验证

Codex 除主程序外还可能启动自己的辅助程序，例如 `codex-code-mode-host`（名称以实际安装包和系统弹窗为准）。它属于 Codex，不是 MyTerm 的 `--myterm-mcp` 进程。[OpenAI 的 App Server 文档](https://learn.chatgpt.com/docs/app-server)说明其默认启动本地 Code Mode host。已收到辅助程序被系统拦截、导致工具发现失败的反馈，但仅凭 `host exited during handshake` 不能断定所有同类错误都是权限问题。

可以提前完成首次验证和必要的放行，但 MyTerm 无法替用户预先授予所有外部程序或未来版本的系统权限。当前应用不会自动完成下面的 Codex 辅助程序验证。

1. 从可信来源完整安装 Codex，在 MyTerm 的“Codex 配置”中确认 CLI 路径；不要只复制主程序或混用不同版本的辅助程序。需要代理时先配置 MyTerm 的独立 Codex 代理。
2. 从 MyTerm 登录并实际启动一个新的 SSH 分析 Codex 标签。选择测试 SSH 会话，取消“允许执行 SSH 命令”和“接入时读取已有输出”。输入：“只发现 MyTerm MCP 工具并确认关联的 SSH 会话；不要读取终端输出，也不要执行 SSH 命令。”这一步验证实际调用链，可能消耗正常的 Codex 使用额度。仅运行 `codex --version`、检查登录或启动本地工作标签，不能替代 SSH 接入验证。
3. 如果 macOS 弹窗点名 Codex 辅助程序，记录准确名称和提示。对于无法验证开发者／无法检查恶意软件的提示，确认安装来源可信后，按 [Apple 的放行步骤](https://support.apple.com/en-us/102445)，在尝试启动后进入“系统设置 → 隐私与安全性 → 安全性 → 仍要打开”，并确认“打开”。文件夹或本地网络访问提示应按对应权限处理；文件损坏或恶意软件警告不要直接套用放行步骤。受组织管理的 Mac 可能需要 IT 处理。
4. 放行后关闭失败的 Codex 标签，重新启动并重复上述工具发现测试。成功标准是 Codex 实际发现 MyTerm 工具并确认选中的会话，而不只是登录成功或 MyTerm 检查显示通过。
5. 若仍失败，在“帮助 → 终端诊断”开始新记录，再复现并导出诊断包。反馈准确时间、系统提示和被拦程序名称、Codex 版本及 MCP 检查结果；不要附登录码、令牌或密码。MyTerm 的日志不一定能记录 Codex 辅助程序在工具调用前的失败，系统提示需要另行提供。

同一软件的放行例外通常会被系统保留，不必每次启动重新操作；但 Codex 更新、辅助程序替换、安装路径或宿主变化、组织策略变化后，可能需要重新验证。仅更新 MyTerm 并不意味着必须重新授权未变化的 Codex。建议安装或升级 Codex 后做一次上述测试，避免到正式排障时才发现问题。稳定签名与公证需要对应软件的发布方处理；给 MyTerm 签名不等于给 Codex 辅助程序签名或授权。

MyTerm 的“检查 SSH MCP 接口”直接启动 MyTerm MCP 进程并检查 `initialize` / `tools/list`，不会启动 Codex 的 Code Mode host。因此它通过，仍不保证 Codex 自身的辅助程序能运行。放宽 SSH 命令审批、开启完全磁盘访问或关闭 Gatekeeper 都不是解决此问题的通用办法。

## 如何检查

在“Codex 配置 → SSH MCP 接口 → 检查 SSH MCP 接口”查看实际辅助进程启动、MCP 初始化和工具发现结果。只有实际启动被拒绝时才提示权限不足。下载隔离标记、代码签名及 Gatekeeper 评估仅保留在诊断包中，不显示在 MCP 状态页面，也不参与接口成功与否的判定。检查只读，不修改系统策略；不会请求全部权限，也不会读取 SSH 输出或执行命令。

签名通过只说明包完整性，不等于 Developer ID 签名或 Apple 公证。Gatekeeper 未通过也不证明本次被拦截：临时签名应用可能已经被用户手动放行。只有实际启动返回 `permission_denied` 等错误，或对应系统提示，才能支持权限拒绝的判断。没有隔离标记也不能证明所有权限正常。

检查后再导出“帮助 → 终端诊断”包，其中 `mcpSecurity` 包含本次安全评估的时间、布尔状态与工具退出码；字段缺失或 `null` 表示本次应用启动后尚未检查。安全工具的退出码为 `null` 表示未能启动或超时，不当成通过。记录不包含原始系统输出、用户路径或凭据。MCP 生命周期记录需要先点击“开始新记录”，再启动出问题的 Codex 标签。

macOS 没有供本应用统一读取所有 TCC 权限状态的公开接口；上述检查不能判定另一台机器、另一个 Codex/IDE 宿主或全部受保护文件夹的授权。若仍失败，请提供发生时间、系统弹窗原文（被拦程序名称）、检查结果，以及是否更新过或运行了另一份 MyTerm。当前应用的检查不能证明外部 Codex 正在调用相同路径。

Apple 建议 macOS 程序使用 Apple 签发的签名身份，以便本地网络隐私机制稳定识别应用；临时签名与版本更新是需要排查的因素，不足以单独证明此次故障根因。

参考：[安全打开应用](https://support.apple.com/en-us/102445)、[文件访问保护](https://support.apple.com/en-ca/guide/security/secddd1d86a6/web)、[本地网络隐私说明](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)。

诊断包包含中文 `诊断摘要.txt` 和英文 `Diagnostic-Summary.en.txt`，请先阅读其中的已观察阶段、影响、建议与判断边界；`diagnostic.json` 保留原始错误码和带时间的 `mcpHealth` 主动检查结果。Codex 接口检查页面也显示可读说明，数字技术详情默认收起。正常 EOF 或 Gatekeeper 未通过不会被单独认定为故障根因。主动检查与辅助进程事件分别解释，缺少事件不代表检查通过。摘要采用本机固定规则，不调用模型，不包含终端正文或凭据。
